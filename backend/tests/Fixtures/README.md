# Test fixtures

Small, real image files used by the validation, thumbnail and metadata tests. All of them are
generated by [`generate.php`](generate.php); do not edit them by hand.

```bash
make fixtures   # runs tests/Fixtures/generate.php inside the php container
```

`tests/Unit/FixturesTest.php` pins the properties listed below, including the PHP behaviour in
the last section, so a regenerated or replaced fixture that drifts (dimensions, format, lost
metadata) fails there before it breaks anything else. In tests, reference fixtures with
`fixture_path('valid.jpg')` (defined in `tests/Pest.php`).

## How they are made

- **Pixels** come from Imagick: a vertical gradient (blue at the top, orange at the bottom), so
  a rotated thumbnail is visibly different from an unrotated one. Every profile, comment and
  timestamp is stripped, so the output is deterministic. The exact bytes depend on the
  ImageMagick version (7.1 in the `php` image). Tests check properties, never hashes.
- **Metadata** is written byte by byte. Imagick's TIFF writer ignores `tiff:make`/`exif:*`
  properties and cannot write chosen raw EXIF values, and it drops the EXIF profile of a
  stripped PNG. So the script has a minimal little-endian TIFF/IFD encoder. EXIF is itself a
  TIFF structure, so the same encoder builds:
  - the TIFF fixtures;
  - the JPEG `APP1` payload;
  - the PNG `eXIf` chunk (spliced in before `IDAT`, with its CRC);
  - the WebP EXIF profile. Imagick writes this one correctly: a `VP8X` flag plus an `EXIF`
    chunk holding the bare TIFF structure.

  IPTC-IIM goes into JPEG with PHP's native `iptcembed()` (Photoshop 3.0 / 8BIM `0x0404`
  `APP13`) and into TIFF as tag 33723 (IPTC-NAA).
- The EXIF blocks carry the tags Exif 2.32 marks as mandatory: ExifVersion, FlashpixVersion,
  ColorSpace and PixelX/YDimension. JPEG also gets YCbCrPositioning and ComponentsConfiguration.
- **TIFF** files are RGB 8-bit, a single Adobe Deflate (`zlib`) strip, a few KB each.
- **`multipage.tiff`** is written by Imagick itself (two images in one wand). Its TIFF coder
  honours only the writer-level `setCompression()` for multi-image output, as with BMP.
- **Not committed:** oversized files (> 5 MB) and images beyond the maximum resolution are
  built at runtime by `jpeg_of_size()` (a fixture padded after the JPEG EOI marker) and
  `png_of_dimensions()` in `tests/Pest.php`. Files whose name doesn't match their content (for
  example, a PDF named `.jpg`) are uploads of the fixtures here under another client name.
  Tests upload them as real `UploadedFile`s via `uploaded_fixture()`, never
  `UploadedFile::fake()`, which reports a MIME type derived from the name.

**"Camera" EXIF** (`exif-iptc.tiff`, `exif.png`, `exif.webp`):
- IFD0: `Make` `FixtureCam`, `Model` `FixtureCam 500`, `Software`, `DateTime`, `Artist`
  `Jan Kowalski`, and resolution 72 dpi. Exception: in `exif.webp`, ImageMagick rewrites
  `XResolution`/`YResolution`/`ResolutionUnit` from the image's own (stripped, zero)
  resolution when it writes the profile, so they read `0/1` and `1` there.
- Exif sub-IFD: `ExifVersion` `0232`, `DateTimeOriginal` `2024:05:01 12:34:56`,
  `FlashpixVersion`, `ColorSpace` sRGB, `PixelX/YDimension`.

### `exif-iptc.jpg` in detail

Marker layout is camera-style: `SOI, APP1 (Exif), APP13 (IPTC), DQT…`. Imagick's JFIF `APP0`
is dropped because both specs claim the slot right after SOI.

- **IFD0:** `Make` = `"Caf\xE9 Optics"` (**Latin-1, invalid UTF-8**), `Model` =
  `FixtureCam 500`, `Orientation` = 6, X/YResolution 72 dpi, `Software`, `DateTime`,
  `YCbCrPositioning`.
- **Exif sub-IFD:** the mandatory tags (PixelX/YDimension = 640×500), `DateTimeOriginal`
  `2024:05:01 12:34:56`, `MakerNote` (8 opaque binary bytes), `UserComment` (undefined charset
  header followed by the same **binary bytes**, including `0x00` and `0xFF`).
- **IPTC:** `1:00` ModelVersion, `1:90` CodedCharacterSet = `ESC % G` (UTF-8), `2:00`
  RecordVersion, `2:05` ObjectName and `2:25` Keywords (repeated, with Polish diacritics),
  `2:80` By-line, `2:116` Copyright (`©`), `2:120` Caption.

Because of the invalid UTF-8 and binary values, `json_encode(exif_read_data(...))` **fails**
on this file with `JSON_ERROR_UTF8`. That is intentional: it is what the metadata sanitizer
must handle.

## Observed PHP behaviour per format (PHP 8.4 `ext-exif`, Imagick 7.1)

The limits in this table are limits of **PHP's APIs**, not of the formats. PNG and WebP can
carry EXIF, and TIFF can carry IPTC.

| Format | `exif_read_data()` | IPTC | Imagick `getImageProfiles()` |
|---|---|---|---|
| JPEG | supported; without EXIF it returns only `FILE`/`COMPUTED` | `getimagesize()` `APP13` → `iptcparse()` | `exif`, `iptc`, `8bim` |
| TIFF | supported; **always** returns baseline IFD0 tags (ImageWidth, BitsPerSample, StripOffsets…), even with no "real" metadata | raw `IPTC/NAA` key of `exif_read_data()` → `iptcparse()` (no `APP13`) | `iptc` (EXIF is exposed as `tiff:*`/`exif:*` properties, not a profile) |
| PNG, WebP | `false` + warning `File not supported`, **even with EXIF present** | — | `exif` |
| BMP, GIF | `false` + warning `File not supported` | — | — |

Further details that matter for metadata extraction:

- An unrecognised `MakerNote` (unknown manufacturer) comes back as a key with the value `null`.
  PHP only decodes maker notes of a few known vendors, so the raw bytes are not available
  through ext-exif.
- `UserComment` comes back as the raw bytes, including its 8-byte charset header.
  `COMPUTED.UserCommentEncoding` reports the charset (`UNDEFINED` here).
- `Make` and other `ASCII` values come back verbatim; PHP does not transcode or validate them.
- ext-exif uses Exif 2.1 names for some tags, e.g. `PixelXDimension`/`PixelYDimension` →
  `ExifImageWidth`/`ExifImageLength`, `FlashpixVersion` → `FlashPixVersion`.

## What the metadata extractor returns per format

`NativeImageMetadataExtractor` (`app/Services/Images`) builds on the behaviour above so that
every format yields the same shape: `exif` holds ext-exif's sections (`IFD0`, `EXIF`, `GPS`,
…) without the PHP-computed `FILE` and `COMPUTED`, and `iptc` holds `iptcparse()` output.
Values that are not valid UTF-8, or that contain C0 control characters other than tab, LF and
CR (binary data such as the IPTC record version `\x00\x04`), are stored as `{"base64": "…"}`.

| Format | EXIF source | IPTC source |
|---|---|---|
| JPEG | `exif_read_data()` on the bytes | `APP13` via `getimagesizefromstring()` |
| TIFF | `exif_read_data()` on the bytes (structural IFD0 tags included) | tag 33723 `IPTC/NAA`, removed from `exif` when it parses (kept raw otherwise); a LONG-typed tag (Photoshop) is repacked in the file's byte order |
| PNG | `eXIf` chunk, parsed as a TIFF stream | — |
| WebP | RIFF `EXIF` chunk, parsed as a TIFF stream (Imagick's `pingImage()` doesn't expose it) | — |
| BMP | — | — |

Damaged metadata never fails an upload: ext-exif's warnings are muted and whatever it could
read is kept (e.g. IPTC survives a broken EXIF IFD); chunk lengths are bounds-checked. An
empty `exif` or `iptc` map is left out of `toArray()`, since PHP would encode it as `[]`.

Known limitations (PHP's APIs, not the formats):

- **Multi-page TIFF:** ext-exif reads only IFD0 and IFD1 and names IFD1 `THUMBNAIL` (its
  JPEG meaning); in a TIFF that is page 2. Pages 3+ are not read (`multipage.tiff` pins this).
- **`MakerNote`** of an unknown vendor comes back as `null`, so its raw bytes are lost.
- **JPEG IPTC** split across several `APP13` segments: PHP keeps only the first one.
- **PNG `tEXt`/`zTXt` "Raw profile type exif/iptc"** chunks (hex-encoded, an ImageMagick
  and exiftool convention, not part of the PNG spec) are not read. XMP is out of scope.
